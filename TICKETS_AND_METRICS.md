# Тикеты и метрики: полное руководство

Документ описывает три вещи:

1. Что мы считаем тикетом и по какой логике.
2. Как устроен пайплайн обработки тикетов.
3. Как считаются метрики тикета: resolution time, handoff time и остальные.

Источник истины по логике: код в `compute_tickets.py`, `resolution_metrics.py`, `ai_analysis.py`, `fine_subcategory.py`, `scheduler.py`. Если документ и код расходятся, прав код.

## Часть 1. Что такое тикет и как мы его считаем

### 1.1. Главный принцип: 1 тикет ≠ 1 диалог

Один диалог может давать несколько тикетов. Правило зависит от стороны обращения (`side`), которую проставляет классификатор.

| Сторона (`side`) | Сколько тикетов из одного диалога |
|---|---|
| `executor` (пишет исполнитель) | всегда **1 тикет** |
| `customer` (пишет заказчик) | **max(1, число групп исполнителей)** |

Логика customer-стороны: заказчик в одном чате может писать про нескольких разных исполнителей. Каждый такой исполнитель это отдельное обращение поддержки.

### 1.2. Методология E (текущая) против методологии D (историческая)

В коде есть две методологии подсчёта customer-стороны. Сейчас используется **E**. Константа: `METHODOLOGY = "E"` в `compute_tickets.py`.

**Методология D.** Считаем число уникальных внешних email исполнителей во всём тексте диалога. `count = max(1, число уникальных email)`. Функция `_executor_emails`.

**Методология E (текущая).** Считаем «группы» исполнителей. Email, перечисленные в ОДНОМ сообщении, это один тикет. Email из РАЗНЫХ сообщений это разные тикеты. Реализовано как число компонент связности графа: вершина это email, ребро соединяет адреса, упомянутые вместе в одном сообщении. Один и тот же адрес в разных сообщениях остаётся одной вершиной и лишний тикет не создаёт. Функция `_executor_email_groups`.

Разница на примере. Заказчик написал два сообщения. В первом два email вместе, во втором ещё один email.
- По D: 3 уникальных email = 3 тикета.
- По E: первая группа (2 email вместе) = 1 тикет, второе сообщение = 1 тикет. Итого 2 тикета.

Набор диалогов у D и E одинаковый. Меняется только `count` для customer-стороны.

### 1.3. Какие email считаются «внешними»

Считаем только email реальных исполнителей. Служебные адреса отбрасываем. Функция `_is_internal_email`.

Исключаются:
- Точные домены: `chatapp.online`.
- Домены с префиксом: `madetask.`, `made-task.`, `remozo.`.
- Локальные части (до `@`): `support`, `info`, `hello`, `noreply`, `no-reply`, `admin`.

Регулярка адреса: `[\w.+\-]+@[\w.\-]+\.[a-z]{2,}`.

### 1.4. Что исключается из подсчёта

Диалог не становится тикетом, если срабатывает хотя бы один фильтр ниже.

**Категории-исключения.** `EXCLUDE_CATEGORIES = {"Тест", "Другое", "Рассылка", "Дубль"}`. Внимание: в текущем коде «Другое» исключается. Старый файл `METHODOLOGY.md` говорил обратное, он устарел.

**Внутренние чаты платформы.** `client_id` начинается с `25ee7201` или `ed3c0fcd`. Это служебные group-чаты MadeTask / Remozo.

**Автоматические фиды.** `chat_name` вида `Wallet <адрес> transactions`. Это системный лог USDT-транзакций, не обращение. Регулярка `EXCLUDE_CHATNAME_RE`.

**Рассылки (broadcast).** Диалог исключается, если ВСЕ входящие сообщения это рассылка. Ключевые слова `BROADCAST_KEYWORDS`: «государственный выходной», «банковские выходные», «пополнение баланса недоступно», «планируйте пополнение», «платформа скоро переедет», «технические работы на стороне провайдеров» и другие. Функция `_is_broadcast`. Если входящих нет вовсе, это тоже не тикет.

**Служебный шум.** Диалог исключается, если КАЖДОЕ входящее после чистки пустое. Чистка убирает префикс автора и служебные слова: `/start`, `/stop`, приветствия, «спасибо», «ок», «понял», эмодзи и пунктуацию. Функции `_strip_noise`, `_is_service_noise`.

**Квалификация по методологии D.** Диалог считается тикетом только если в нём есть хотя бы одно содержательное входящее сообщение ИЛИ категория = `KYC`. Функция `_qualifies_d`. Порядок хранения сообщений не важен: Flomni отдаёт историю новыми сверху, ChatApp старыми сверху, поэтому проверяем наличие предметного inbound, а не первое сообщение.

### 1.5. Дедупликация

**По ключу (client_id, dialog_date).** Из записей с одинаковым клиентом и датой остаётся одна, с бо́льшим `messages_count`.

**Кросс-кабинетная (только Flomni).** Один и тот же групповой Telegram-чат приходит в двух Flomni-кабинетах под разными `client_id`. Схлопывать только по «компания + день» нельзя: у компании легитимно бывает несколько разных чатов за день. Признак дубля это совпадение СОДЕРЖАНИЯ переписки. Функция `_dedupe_cross_cabinet`. Критерии:
- не менее 4 общих содержательных сообщений (`_DEDUP_MIN_SHARED`);
- у обоих диалогов не менее 4 таких сообщений (`_DEDUP_MIN_SIZE`);
- вложенность меньшего множества в большее не ниже 0.9 (`_DEDUP_MIN_CONTAINMENT`);
- компании совместимы по токенам (`_company_compatible`), чтобы не склеить разные фирмы с общим текстом.

Из пары остаётся чат с групповым именем «…MadeTask», иначе с бо́льшим `messages_count`.

### 1.6. Куда пишется результат: таблица `tickets`

`compute_tickets.py` удаляет старые строки в диапазоне дат и вставляет новые. Апсерт по `(dialog_id, methodology)`, поэтому повторный прогон идемпотентен.

Ключевые поля строки: `dialog_id`, `methodology`, `count`, `side`, `category`, `company`, `dialog_date`, `source`, `executor_emails`, `computed_at`.

### 1.7. Порядок фильтров в `compute()`

1. Загрузка классифицированных диалогов (`processed=true`, есть side и category), для каждого dialog_id берётся последний `analysis_result`.
2. Убрать внутренние чаты.
3. Убрать категории-исключения.
4. Убрать авто-фиды по `chat_name`.
5. Дедуп по `(client_id, dialog_date)`.
6. Кросс-кабинетная дедупликация Flomni.
7. Для каждого оставшегося: проверка broadcast, проверка шума, проверка квалификации D.
8. Подсчёт `count` и вставка в `tickets`.

### 1.8. Запуск

```bash
docker exec -i support_tickets-scheduler-1 \
  python compute_tickets.py --date-from 2026-07-01 --date-to 2026-07-31
```

Без дат пересчитываются все классифицированные диалоги.

## Часть 2. Пайплайн обработки тикетов

### 2.1. Источники данных

- **Flomni.** Реалтайм через вебхук плюс подтягивание истории по расписанию.
- **ChatApp.** Инкрементальная выгрузка истории по расписанию.
- **Bitrix.** Исторический архив (таблица `bitrix_messages_raw`), в текущем потоке не пополняется.

### 2.2. Вебхук (сервис `webhook`)

FastAPI-приложение `main:app`, файл `main.py`. Эндпоинты:
- `POST /webhook/flomni` принимает и Flomni, и ChatApp (диспатч по форме payload через `detect_source`).
- `GET /health` проверка живости.

Что делает обработчик Flomni (`webhooks/flomni.py`):
1. Проверяет HMAC-подпись, если задан `FLOMNI_WEBHOOK_SECRET`. Если секрет пуст, подпись не проверяется.
2. Складывает входящее в `IncomingMessage`, аккумулирует текст в открытую запись клиента.
3. Постит сообщение в Slack (новый тред или ответ в существующий).
4. Для содержательных обращений запускает AI-черновик ответа.

Есть fallback против кросс-коннекторных дублей Telegram: если один и тот же чат приходит под разными `receiver`, но с тем же именем канала, второе сообщение маршрутизируется в существующую запись.

### 2.3. Расписание (сервис `scheduler`)

`scheduler.py`, APScheduler, часовой пояс UTC. Задачи с суточным окном и `misfire_grace_time = 24h` (чтобы не терять запуск при простое хоста).

| Время (UTC) | Задача | Функция | Что делает |
|---|---|---|---|
| 02:00 | Flomni history | `flomni_history.run` | тянет историю сообщений Flomni |
| 02:30 | ChatApp history | `chatapp_history.run_daily` | инкремент за последние 25 часов, идемпотентно по (чат × день) |
| 04:00 | AI analysis | `ai_analysis.run` | классификация: side, category, subcategory |
| 05:00 | Company attribution | `company_attribution.run` | атрибуция компании: email → Superset → имя группы |

При старте до входа в цикл вызывается `flomni_history.detect_gap_and_backfill()` для восстановления после простоя.

### 2.4. Классификация (`ai_analysis.py`)

`run()` берёт диалоги с `processed = False`, вызывает OpenAI и пишет строку `analysis_results`, затем ставит `processed = True`. Идемпотентно: уже обработанные диалоги пропускаются.

Что определяется:
- **side**: `customer` или `executor`. Есть детерминированные признаки (групповой чат или несколько email исполнителей обычно означают customer), остальное решает LLM.
- **category**: одно значение из списка, свой для каждой стороны.
- **subcategory**: детализация внутри категории, только для категорий из словаря `SUBCATEGORIES`.

Категории customer: KYC, «Выплаты и проблемы с ними», «Техническая проблема/вопрос», «Запрос документов», «Зачисление платежа на баланс», «Вопросы по числам отправки закрывашек в эдо…», «Вопросы по работе в сервисе», «Функциональность сервиса и возможность выплат», «Изменения в профиле…», «Налоговый статус исполнителя», «Потенциальный клиент», «Другое».

Категории executor шире (KYC, «ИП РФ», «SEPA/SWIFT», «НДФЛ», «EOR», «Реквизиты заблокированы», «Тест» и другие).

Важно про историю. Реалтайм-вебхук раньше ставил английские категории (Account/Billing/Technical/Other) и тоже выставлял `processed = True`. Такие диалоги `ai_analysis.run` повторно не трогает, пока `processed` не сброшен в False.

### 2.5. Детальные подкатегории (`fine_subcategory.py`)

Внутри AI-подкатегории делается ещё более тонкая разбивка на «бакеты» набором упорядоченных регулярок по тексту диалога (сообщения + summary + rationale). Первое совпадение выигрывает, последний бакет это `_FALLBACK`.

Особенности:
- Бакеты заданы по AI-подкатегории (`_BUCKETS_BY_SUB`), но в отчёте и при хранении используется отображаемое имя (`DISPLAY_SUB`), поэтому две AI-подкатегории могут схлопываться в одну (например слияние KYC).
- Результат по каждому диалогу пишется в `dialog_fine_subcategory` (PK `dialog_id`) скриптом `compute_fine_subcategory.py`.
- Есть особый бакет «Пополнение/депозит», который в отчёте выносится в отдельную категорию (зачисление на баланс заказчиком, а не выплата исполнителю).

### 2.6. Ручные корректировки для отчёта

Отчёт (`build_july_report.py`) поверх данных применяет слои:
- `manual_category_override` исправляет мисклассификацию категории;
- `manual_subcategory_override` проставляет подкатегорию диалогам без AI-подкатегории;
- carve-out депозитов из бакета «Пополнение/депозит».

Эффективная категория: `COALESCE(override, deposit, ticket.category)`.

### 2.7. Схема потока данных

```
Flomni webhook ─┐
                ├─> incoming_messages ─┐
Flomni history ─┘                      │
                                       ├─> dialogs ─> ai_analysis ─> analysis_results
ChatApp history ───────────────────────┘                                   │
                                                                            ▼
                                              compute_tickets ──> tickets ──┤
                                              compute_fine_subcategory ──> dialog_fine_subcategory
                                              compute_resolution_metrics ──> ticket_resolution_metrics
                                                                            │
                                                                            ▼
                                                              build_july_report ──> HTML/PDF
```

### 2.8. Основные таблицы

| Таблица | Что хранит |
|---|---|
| `incoming_messages` | сырые входящие из вебхука, состояние тредов Slack |
| `dialogs` | собранные диалоги с `messages_json`, `client_id`, `company`, `source` |
| `analysis_results` | результат классификации: side, category, subcategory, summary |
| `tickets` | посчитанные тикеты (одна строка на dialog_id × methodology) |
| `dialog_fine_subcategory` | детальный бакет по диалогу |
| `ticket_resolution_metrics` | метрики по инцидентам (см. часть 3) |
| `chatapp_messages_raw`, `bitrix_messages_raw` | сырьё источников |

## Часть 3. Метрики тикета

Весь расчёт в `resolution_metrics.py`. Прогон и запись в БД в `compute_resolution_metrics.py`.

### 3.1. Вход и нормализация

На вход список сообщений вида `{"text", "direction": "inbound|outbound", "time": ISO8601}`. Модуль не зависит от источника.

Нормализация (`normalize`):
- парсинг времени в UTC;
- чистка префикса автора «@user Имя:» из групповых чатов;
- дедупликация повторов (Flomni иногда шлёт дубли);
- сортировка по времени;
- реклассификация: в группах CSM или аккаунт-менеджер приходит как inbound, но считается стороной поддержки (support).

### 3.2. Сегментация на инциденты

Один диалог режется на отдельные ИНЦИДЕНТЫ, чтобы не склеивать разные обращения одного клиента. Функция `segment_incidents`.

Правило: новый инцидент начинается, если пауза между соседними сообщениями больше `INCIDENT_GAP_HOURS = 24` И следующим пишет клиент. Поздний ответ поддержки после паузы это продолжение прежнего инцидента, а не новый.

Одна строка в `ticket_resolution_metrics` = один инцидент. Апсерт по `(dialog_id, incident_index)`, прогон идемпотентен. Инцидент без содержательного обращения клиента пропускается.

### 3.3. Метрики по инциденту (`TicketMetrics`)

| Поле | Смысл |
|---|---|
| `started_at` | старт: первое содержательное входящее клиента |
| `first_response_at` / `first_response_seconds` | время до первого содержательного ответа поддержки |
| `resolved_at` / `resolution_seconds` | время до фактического решения (календарное) |
| `resolution_working_seconds` | то же решение, но только в рабочие часы поддержки |
| `handoff_seconds_by_dept` | время в каждом смежном отделе |
| `handoff_seconds_total` | суммарное время во всех передачах |
| `status` | итоговый статус инцидента |
| `n_messages` | число сообщений в инциденте |

### 3.4. First response time

Первый содержательный ответ поддержки после старта. Заглушки не считаются ответом. Заглушки это:
- шаблоны-холды `HOLD_TEMPLATES`: «мы получили ваше сообщение», «скоро ответим», «уточняем информацию… ожидайте», «still working on your request» и подобные;
- приветствия без сути `GREETING_NOISE` (считаются шумом, только если после их вырезания ничего не осталось);
- системные авто-логи кошелька `SYSTEM_FEED_PATTERNS`.

Сообщение с признаком решения заглушкой не считается: решение важнее.

### 3.5. Resolution time

Время от старта до РЕШЕНИЯ. Обещания «взяли в работу», «вернёмся с ответом» это не решение (`PROMISE_PATTERNS`). Решение фиксируется по одному из признаков (берётся последнее по времени подходящее сообщение):

1. **Явный маркер поддержки** `RESOLUTION_DONE`: «выплата проведена/выполнена», «реквизиты подтверждены», «баланс пополнен», «верификация проведена», «has been processed/completed» и другие. Учитываются отрицания (`_NEG_RESOLUTION` снимает ложное срабатывание).
2. **Подтверждение клиента** `CLIENT_RESOLUTION`: «платёж дошёл», «деньги пришли», «всё работает». Голое «спасибо» сюда не входит.
3. **Ролевое доопределение**, если явного маркера нет:
   - последнее содержательное сообщение это ответ поддержки (утверждение, не вопрос и не запрос данных) → решено;
   - клиент последним подтвердил закрытие (`CLIENT_CLOSE`) → решено;
   - клиент ответил отрицанием на вопрос поддержки «ещё актуально?» (`ACTUALITY_Q` + `CLIENT_NEG_CLOSE`) → решено;
   - клиент подтвердил резюме поддержки (`CLIENT_CONFIRM`: «всё верно») при осмысленном предыдущем ходе поддержки → решено;
   - клиент принял ответ (`CLIENT_ACK`: «понятно/окей») при реальном ответе поддержки перед этим → решено.

Отдельное правило: явное закрытие клиентом важнее незакрытой передачи в отдел. Если клиент удовлетворён, внутренняя передача уже не важна.

Календарное и рабочее время считаются от `started_at` до `resolved_at`.

### 3.6. Handoff time (время в смежных отделах)

Сколько вопрос провёл в других отделах. Функция `_extract_handoffs`. Ищем в сообщениях ПОДДЕРЖКИ:
- **открытие передачи** `HANDOFF_OPEN` по отделам:
  - `compliance` (комплаенс, служба безопасности, отдел проверки),
  - `finance` (финотдел, казначейство, бухгалтерия),
  - `documents` (документооборот),
  - `legal` (юридический),
  - `bank_provider` (банк, платёжный провайдер),
  - `technical` (технический отдел, разработка);
- **закрытие передачи** `HANDOFF_CLOSE`: «коллеги подтвердили», «получили ответ», «проверка завершена», либо факт решения.

Для каждой передачи считается длительность (от открытия до закрытия). Незакрытые передачи остаются открытыми и держат статус `pending_department`. Есть защита: на сообщении-решении новая передача не открывается, чтобы упоминание отдела в тексте решения («согласовано с финансовым отделом») не переоткрывало только что закрытую передачу.

Итоги: `handoff_seconds_by_dept` по отделам и `handoff_seconds_total` суммарно.

### 3.7. Рабочее время

`working_seconds` считает секунды только внутри графика поддержки:
- часовой пояс MSK (`WORK_TZ`);
- часы 10:00-19:00 (`WORK_START`, `WORK_END`);
- дни Пн-Пт (`WORK_DAYS`).

Ночи, выходные и время вне графика не входят в `resolution_working_seconds`. Календарный `resolution_seconds` считает всё подряд.

### 3.8. Статус инцидента

Функция `_status`, приоритет сверху вниз:

| Статус | Условие |
|---|---|
| `resolved` | найдено решение (`resolved_at` заполнено) |
| `pending_department` | есть незакрытая передача в смежный отдел |
| `awaiting_support` | последним содержательным писал клиент, ждём поддержку |
| `awaiting_client` | последним содержательным писала поддержка, ждём клиента |
| `open` | не удалось определить чей ход |
| `no_client_message` | в инциденте нет обращения клиента |

Хвостовой клиентский филлер («подожду», «буду ждать») при определении «чей ход» игнорируется: он не требует ответа.

### 3.9. Куда пишется: таблица `ticket_resolution_metrics`

Поля: `dialog_id`, `incident_index`, `client_id`, `source`, `dialog_date`, `company`, `started_at`, `first_response_at`, `resolved_at`, `first_response_seconds`, `resolution_seconds`, `resolution_working_seconds`, `handoff_seconds_total`, `handoff_by_dept` (JSON), `status`, `n_messages`, `computed_at`.

База для прогона это отчётные тикеты: берутся диалоги, у которых есть строка в `tickets` за период (через EXISTS, без привязки к конкретной методологии, чтобы не задваивать при наличии и D, и E).

### 3.10. Запуск

Прогон и запись в БД:
```bash
docker exec -i support_tickets-scheduler-1 \
  python compute_resolution_metrics.py --date-from 2026-07-01 --date-to 2026-07-31
```

Разбор одного диалога для отладки (без записи в БД):
```bash
docker exec -i support_tickets-scheduler-1 python resolution_metrics.py --dialog-id 3244
docker exec -i support_tickets-scheduler-1 python resolution_metrics.py --client-id <hash> --json
```

## Часть 4. Типовой порядок пересчёта

Когда пришли новые диалоги и их нужно превратить в отчётные тикеты с метриками:

1. `ai_analysis.run` (или дождаться крона в 04:00) классифицирует новые диалоги.
2. `compute_tickets.py --date-from … --date-to …` считает тикеты.
3. `compute_fine_subcategory.py` проставляет детальные бакеты.
4. `compute_resolution_metrics.py --date-from … --date-to …` считает метрики.
5. `build_july_report.py` собирает HTML, дальше рендер в PDF через Chrome headless.

Все шаги идемпотентны, повторный прогон безопасен.

## Частые ошибки

| Ошибка | Правильно |
|---|---|
| Считать `COUNT(*)` диалогов | применять логику `count_tickets` (email-группы для customer) |
| Считать «Другое» как тикет | в текущем коде «Другое» исключается |
| Не дедуплицировать Flomni | дедуп по `(client_id, dialog_date)` плюс кросс-кабинетный по контенту |
| Считать рассылки и `/start` за обращения | их отсекают `_is_broadcast` и `_is_service_noise` |
| Считать заглушку «ожидайте» за first response | заглушки из `HOLD_TEMPLATES` не считаются ответом |
| Считать «взяли в работу» за решение | это обещание (`PROMISE_PATTERNS`), не решение |
| Мерить resolution только календарно | есть и рабочее время (Пн-Пт 10:00-19:00 MSK) |
