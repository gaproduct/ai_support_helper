# Передача данных саппорта в Superset

Состояние на 25 августа 2026. База `support_tickets`, PostgreSQL 16.

## Что забирать

Три вьюхи. Больше ничего не нужно.

| Объект | Строк | Гранулярность | Период |
|---|---|---|---|
| `mart_tickets` | 2955 | Один тикет-диалог | Июнь — август |
| `mart_incidents` | 3025 | Одно обращение внутри диалога | Июнь — август |
| `mart_dialogs_history` | 8340 | Один диалог | Январь — август |

Первые две это основа. Третья нужна только для длинного тренда, у неё свои ограничения, они описаны в отдельном разделе ниже.

Вьюхи уже учитывают все правила подсчёта. Ходить в сырые таблицы не надо: там шесть ловушек, каждая из которых меняет цифру. Они описаны в конце файла.

Определения лежат в `mart_views.sql` в репозитории. Если понадобится пересоздать, применяется так:

```
psql -U postgres -d support_tickets -f mart_views.sql
```

## Главное правило

**Тикет не равен строке.** В `mart_tickets` есть колонка `ticket_count`. У обращений исполнителей там всегда 1, у обращений заказчиков бывает больше: одно письмо может касаться нескольких исполнителей.

```sql
SELECT SUM(ticket_count) FROM mart_tickets;   -- правильно: 3280
SELECT COUNT(*)          FROM mart_tickets;   -- неправильно: 2955
```

Считайте `SUM(ticket_count)` везде, где нужно число тикетов. `COUNT(*)` отвечает на другой вопрос: сколько было диалогов.

## mart_incidents

Диалог режется на обращения по паузе больше 24 часов перед репликой клиента. Ключ составной: `dialog_id` плюс `incident_index`.

Атрибуты `dialog_date`, `source`, `side`, `category`, `subcategory`, `company` продублированы из `mart_tickets`, джойнить не нужно.

| Поле | Тип | Что это |
|---|---|---|
| `started_at` | timestamptz | Начало обращения |
| `first_response_at` | timestamptz | Первый ответ поддержки |
| `resolved_at` | timestamptz | Закрытие |
| `first_response_seconds` | float | Скорость первого ответа |
| `resolution_seconds` | float | Время решения, календарное |
| `resolution_working_seconds` | float | Время решения в рабочих часах |
| `handoff_seconds_total` | float | Сколько суммарно ждали смежные отделы |
| `handoff_by_dept` | jsonb | То же в разрезе отделов |
| `status` | text | `resolved` или нет |
| `n_messages` | int | Сообщений в обращении |

Метрики скорости считать здесь, а не в `mart_tickets`. В диалоге бывает несколько обращений, и усреднять их по диалогу нельзя.

**Про `status`.** Автоопределение «вопрос закрыт» пока ненадёжное. В отчётах для руководства этот показатель не публикуется. Для внутреннего анализа пользоваться можно, для дашборда наверх лучше не выносить.

## mart_dialogs_history

Длинный ряд с января. Нужен для одного вопроса: сколько было обращений и о чём. На остальные вопросы он не отвечает.

Поля: `dialog_date`, `source`, `side`, `category`, `company`, `chat_name`, `summary`, `data_era`.

**Складывать с `mart_tickets` нельзя.** Здесь диалоги, там тикеты. Это разные единицы.

| Месяц | Диалогов | Bitrix | ChatApp | Flomni |
|---|---|---|---|---|
| Январь | 799 | 125 | 674 | 0 |
| Февраль | 879 | 163 | 716 | 0 |
| Март | 1355 | 388 | 967 | 0 |
| Апрель | 1431 | 433 | 822 | 176 |
| Май | 921 | 0 | 288 | 633 |
| Июнь | 1029 | 0 | 331 | 698 |
| Июль | 919 | 0 | 281 | 638 |
| Август | 1007 | 0 | 289 | 718 |

Колонка `data_era` делит ряд надвое: `jan_may` и `jun_aug`. До июня действовала другая методология. Что это значит на практике:

- **Метрик скорости за январь-май нет.** Первый ответ и время решения начали считать с июня. Джойнить историю с `mart_incidents` бессмысленно.
- **Тикетов за январь-май нет.** Их тогда не считали, поэтому вьюха работает на уровне диалогов. Веса `ticket_count` здесь нет.
- **Канал Bitrix жил только до апреля.** 1109 диалогов. Потом закрылся. Если строить тренд по объёму, решите заранее, включать его или нет: без него январь-апрель просядет примерно на пятую часть.
- **Категории января-мая переведены на нынешние.** Тринадцать старых категорий сведены к текущим по разбору текстов обращений. «Проблема KYC» и «Дублирование KYC» в KYC, «Запрос документов не бух» и вопросы по закрывающим документам в «Запрос документов», SEPA/SWIFT и заблокированные реквизиты в «Выплаты», НДФЛ в «Налоговый статус исполнителя», «ИП РФ» в «Статус ИП РФ/Самозанятого», EOR в «Вопросы по работе в сервисе». Служебные «Другое» и «Тест» отброшены.

**Две категории через границу мая-июня читать нельзя.** «Вопросы по работе в сервисе» падают с 753 до 120, «Функциональность сервиса и возможность выплат» с 271 до 12. Это не изменение реальности, а смена поведения классификатора. По остальным категориям ряд ведёт себя ровно.

## Что вьюхи уже сделали за вас

Это те самые шесть правил. Их не надо повторять, но полезно знать, что они есть.

1. **Только методология E.** Способ считать тикеты менялся. Актуальна E, всё остальное из таблицы вычищено 25 августа.
2. **Разметка дедуплицирована.** У диалога бывает несколько прогонов модели, берётся последний. У 141 диалога прогоны давали разные категории, так что выбор не формальность.
3. **Категория итоговая.** Собрана из трёх слоёв: ручная правка, вынос депозитного бакета в отдельную категорию, категория модели. В сырой таблице лежит только третий слой.
4. **Служебные категории убраны.** «Тест», «Другое», «Рассылка», «Дубль», «Без запроса» тикетами не считаются.
5. **Теневые дубли исключены.** 211 строк, где один и тот же чат Telegram пришёл вторым каналом Flomni.
6. **Компании канонизированы.** «Эктивейт» был написан четырьмя способами. Заглушка `Unknown` заменена на NULL.

## Чего в выгрузке нет

**Текста переписки.** Полные диалоги в Superset не уезжают: там шире круг доступа. Для срезов они не нужны, для разбора конкретного кейса есть `summary` и `dialog_id`, по которому диалог можно поднять в исходной базе.

**Тикетов и метрик скорости до июня.** Январь-май есть только на уровне диалогов, во вьюхе `mart_dialogs_history`. Пересчитать те месяцы по нынешней методологии нельзя: исходные данные лежат в другой схеме.

## Ограничения, о которых стоит помнить

- **Компания заполнена у 62% тикетов.** Доли по компаниям считайте от заполненных, а не от всех, иначе занизите.
- **Подкатегория заполнена у 76%.** Она задана не для всех категорий, это нормально.
- **У 376 обращений нет первого ответа.** Поддержка не ответила либо клиент закрыл вопрос сам. В медианах такие строки надо отбрасывать, `percentile_cont` делает это сам.
- **Август неполный.** Данные по 24 августа. Прямое сравнение с полным месяцем занижает показатели.
- **Июнь неполный по людям.** В ChatApp тогда не писалось поле с почтой оператора. Разрез по сотрудникам за июнь несопоставим со следующими месяцами.
- **Один человек под двумя ID считается двумя.** Если клиент написал из Telegram и из личного кабинета, это два тикета. Часть таких дублей снимается, но не все.

## Обновление данных

Вьюхи не материализованы, они всегда показывают текущее состояние базы. Пересчёт тикетов и разметки идёт ночной джобой. Как часто тянуть данные в Superset, решайте сами, раз в сутки достаточно.
