# Правила классификации диалогов поддержки

Документ является единственным источником правил для AI-классификатора (`ai_analysis.py`).
При изменении правил — редактировать только этот файл; промпт обновится автоматически.

> **Как используется файл:**
> - §1 «Определение стороны» и §2 «Категории» — справочник для людей;
>   в промпт **не загружаются** (side-определение и категории встроены в код).
> - §3–§10 — загружаются в LLM-промпт автоматически (между маркерами ниже).
> - §11 «Поля ответа» — справочник для людей; в промпт не загружается.

---

## 1. Определение стороны (`side`)

Определяется по тому, **от чьего имени пишет** автор inbound-сообщения.
`customer` и `executor` — это **разные типы клиентов**, не синонимы.

### `customer` — Заказчик-плательщик

Компания / ИП, которая **платит** через платформу своим исполнителям.

Маркеры в тексте inbound-сообщения:
- Множественное число от лица бизнеса: «у нас», «наша компания», «наши исполнители», «нам нужно»
- Просит сделать что-то **с другим** человеком: «верифицировать нашего исполнителя», «выплата нашему фрилансеру», «зачислить нашему контрактору»
- Называет ФИО / email / id другого человека в третьем лице: «автор Vova@... не может пройти KYC»
- Корпоративный / групповой чат с несколькими сотрудниками компании

> **Правило группового чата (жёсткое):** если inbound пишут **два и более разных автора**
> (префиксы `@user1 …`, `@user2 …`), это корпоративный чат заказчика — **ВСЕГДА `customer`**,
> даже если системный текст процитирован во втором лице («Вас не удалось верифицировать…»).
> Там сотрудники компании ведут обращения сразу за нескольких своих исполнителей
> (часто с разными email вида `performer.*@…`). Один и тот же автор группой не считается.
> «Групповой» — свойство **кабинета (client_id)**, а не дневного среза: авторы
> агрегируются по всем диалогам клиента, поэтому если хоть раз было ≥2 разных автора,
> то ВСЕ диалоги этого кабинета — `customer`. Решение принимается детерминированно
> **до вызова LLM** (`ai_analysis.group_cabinet_ids`): для группового кабинета сторона
> сразу `customer`, а LLM используется только для категории/summary.

### `executor` — Исполнитель / Контрактор

Физлицо или ИП-фрилансер, который **получает** выплаты через платформу.

Маркеры в тексте inbound-сообщения:
- Первое лицо единственного числа про **свою** ситуацию: «я не могу пройти KYC», «не пришла МОЯ выплата», «МОЙ налоговый статус», «my withdrawal»
- Пишет о своём кабинете / своей верификации / своих деньгах / своём ИП-статусе
- Индивидуальный 1:1 чат с одним физлицом
- Потенциальные новые клиенты и незарегистрированные пользователи (исторически заходят со стороны executor)

> **Ключевое правило:** если автор пишет от первого лица про получение СВОЕЙ выплаты / прохождение СВОЕГО KYC / СВОЙ налоговый статус / СВОЙ аккаунт — это `executor`, даже если его можно назвать «клиентом сервиса».
> `customer` — только тот, кто **платит** исполнителям через платформу.

## 3. Приоритет категории: KYC / Верификация

Если в диалоге явно обсуждается **процесс KYC / верификации личности** — выбирать KYC-категорию, даже если симптом сформулирован как «не приходит выплата» / «заблокирована карта».
**KYC — корень, выплата — симптом.**

- обе стороны → «KYC» (единая категория, не «Выплаты и проблемы с ними»)

**Маркеры KYC-темы:**

- «верификация не проходит / не работает / отклонена / в обработке»
- «загрузите паспорт / селфи / документ»
- «фотография паспорта неполная / нечёткая»
- «ошибка permission_denied / verification_failed / kyc_pending»
- явные слова «KYC», «верификация», «верифицировать», «верификационная проверка»

**НЕ относится к KYC:**

- Упоминание «верификации» только в стандартном welcome-сообщении бота / FAQ-ответе — без реальной проблемы клиента
- Подтверждение налогового статуса → «Налоговый статус исполнителя»
- Юридические документы по компании (KYB, договоры) → «Запрос документов»

### Дубликат / объединение профиля

Когда заказчик просит **перенести / продублировать** уже пройденную верификацию исполнителя из одного кабинета в другой, либо объединить дублирующиеся профили:

- «продублировать верификацию из кабинета Линперс в Юнион»
- «продублировать KYC из кабинета A в кабинет B»
- «перенести верификацию исполнителя в другой кабинет»
- «скопировать верификацию / переклонировать KYC»
- «документы отправлены в другой профиль / объедините профили»

→ Категория: **«KYC»**, подкатегория **«Дубликат/объединение профиля»** (см. §10).
Отдельной категории «Дублирование KYC» больше нет — она свёрнута в подкатегорию KYC.

## 4. Разграничение: KYC / Налоговый статус / Техническая проблема

Раздел закрывает наиболее частые ошибки классификации в KYC-бакете.

### KYC — ТОЛЬКО верификация личности

Паспорт, селфи, удостоверение личности, ошибки проверки (permission_denied, kyc_pending), ожидание ручной проверки compliance, отклонённые / нечёткие фото документа.

> Если в тексте **нет** слов «паспорт», «селфи», «удостоверение», «верификация» применительно к документу — это скорее всего **не KYC**.

### НЕ KYC → «Налоговый статус исполнителя» (`customer`)

Если заказчик пишет про налоговый / ИП-статус своих исполнителей:

- «исполнитель сменил статус самозанятого»
- «нужно подтвердить статус ИП»
- «как изменить налоговый статус в профиле»
- «что нужно сделать для подтверждения НПД»

Маркеры: «налоговый статус», «самозанятый», «НПД», «патент», «ИП», «подтверждение статуса», «смена статуса», «закрытие ИП»

### НЕ KYC → «Статус ИП РФ/Самозанятого» / «ИП РФ» / «НДФЛ» (`executor`)

Если исполнитель пишет про **свой** ИП-статус или статус самозанятого:

- «как подтвердить статус самозанятого»
- «я закрыл ИП, что дальше»
- «не могу подтвердить статус в приложении ФНС»
- «нужна справка о постановке на учёт»
- «как поставить / снять статус самозанятого»

> **Ключевое отличие:**
> - KYC = верификация **личности** (паспорт / селфи / identity check)
> - Налоговый статус = подтверждение / изменение **налогового режима** (самозанятость, ИП, НПД, патент, НДФЛ, ФНС)

### НЕ KYC → «Техническая проблема/вопрос» (активация аккаунта)

Проблемы с активацией учётной записи и доступом — техническая проблема, **не KYC**:

- «не могу активировать учётную запись»
- «не приходит письмо с подтверждением регистрации»
- «ошибка при активации аккаунта»
- «аккаунт уже существует»
- «не могу войти», «забыл пароль», «не открывается ЛК»

> KYC = верификация документов **после** успешной регистрации.
> Активация / вход = техническая проблема **на этапе** регистрации/входа.

### НЕ KYC → «Изменения в профиле заказчика/исполнителя» / «Изменение/удаление аккаунта»

Запросы на **смену данных профиля** — это изменения профиля, **не KYC** и **не Техническая проблема**:

- `customer` → **«Изменения в профиле заказчика/исполнителя»**:
  «удалите аккаунт нашего исполнителя», «нужно удалить профиль», «поменяйте ФИО», «обновите реквизиты исполнителя»
- `executor` → **«Изменение/удаление аккаунта»**:
  «хотел бы поменять почту в профиле», «изменить email / телефон / имя», «как удалить аккаунт»

> Правило: если клиент **просит изменить конкретные данные** (email, телефон, ФИО, реквизиты) — это **профиль**, не техническая проблема.
> «Техническая проблема» = не работает сайт / не приходит код / ошибка при входе.

### НЕ KYC → «Налоговый статус исполнителя» (Т-Банк / ФНС / СМЗ)

Если диалог о **подтверждении налогового статуса самозанятого через банк или ФНС** — это «Налоговый статус», **даже если используется слово «верификация»**:

- «проверка СМЗ через Т-Банк», «подписаться под условия Т-Банка», «подтверждение статуса самозанятого через приложение ФНС»
- «пришлите условия изменений НПД», «самозанятый не может подтвердить статус в Т-Банке»

→ Категория: **«Налоговый статус исполнителя»** (`customer`) / **«Статус ИП РФ/Самозанятого»** (`executor`)

## 5. Правила для категории «Потенциальный клиент»

Категория означает: человек, который впервые обращается в сервис с **вопросом о возможности подключения** или **условиях работы** для бизнеса (платить исполнителям через платформу). Это B2B-лид для отдела продаж.

### ⚠️ Правило приоритета

**«Потенциальный клиент» имеет БОЛЕЕ ВЫСОКИЙ приоритет, чем «Выплаты», «Вопросы по работе в сервисе» и «Другое».**

Если пользователь впервые пишет в сервис и спрашивает «можно ли платить», «сколько стоит», «подходит ли ваш сервис для нашей ситуации» — это **«Потенциальный клиент»**, даже если в тексте есть слова «payment», «выплата», «комиссия».

> Ключевое различие:
> - «Не пришла МОЯ выплата» = действующий пользователь → «Выплаты и проблемы с ними»
> - «Можно ли платить моим сотрудникам через вас?» = новый контакт → «Потенциальный клиент»

### Маркировать при выполнении условий 1 + 2 (условие 3 — дополнительный сигнал)

**Условие 1 — Есть содержательный inbound-текст** (не только «/start», не пустые сообщения)

**Условие 2 — Пользователь исследует сервис как потенциальный заказчик**, хотя бы один из маркеров:
- «I'm interested in setting up a service to pay...», «we are considering to hire a contractor»
- «хочу платить сотрудникам / исполнителям / фрилансерам через вас»
- «мы компания / ИП / агентство, хотим подключиться»
- задаёт вопрос «можно ли платить в страну X?», «возможны ли выплаты в Россию?» как первое сообщение
- называет планируемый объём / количество исполнителей: «6–7 сотрудников по $2k+», «до 25 человек», «2 000–2 500 EUR/мес»
- спрашивает комиссию / условия / договор для юрлица как **новый** пользователь
- исполнитель пишет от имени своего незарегистрированного заказчика: «мой заказчик пока не зарегистрирован, просил узнать условия»
- вопрос о применимости модели: «подходит ли ваш сервис для нашей ситуации?», «Is the Remozo model suitable for us?»

**Условие 3 (дополнительный сигнал)** — Поддержка реагирует характерно: спрашивает оборот/объём, предлагает условия (12% комиссия), передаёт персональному менеджеру, пишет «I will write you in TG»

### Реальные примеры «Потенциальный клиент»

| Inbound | Почему лид |
|---|---|
| «I want start with one guy to get 500 usd per month. can grow upto 25 in 2 months.» | Новый пользователь, называет объём, бизнес-контекст |
| «I'm interested in setting up a service to pay salaries to my employees... 6–7 employees and $2k+ each per month» | Прямое намерение подключиться как заказчик |
| «Is it possible to send payments to employees' bank accounts in Russia?» (первый вопрос нового пользователя) | Исследует возможности платформы перед регистрацией |
| «Is the Remozo model suitable for our situation? Will my partner's details appear in closing documents?» | Вопросы о применимости и конфиденциальности перед подключением |
| «Он просил узнать меня всю эту информацию, прежде чем принять решение» | Исполнитель собирает инфо для незарегистрированного заказчика |

### НЕ маркировать как «Потенциальный клиент»

- Диалог состоит только из «/start» + welcome-бот без содержательного ответа
- Действующий пользователь спрашивает про **свою** выплату / KYC / лимит / закрывающие документы (уже работает с платформой)
- «я исполнитель / фрилансер / хочу получать выплаты» (executor, не заказчик)
- Физлицо вне B2B-контекста: личные документы, подтверждение доходов для визы
- Внутренние сообщения сотрудника платформы (`@madetask`, `@remozo`, `RemozoSupport`)
- Представление нового менеджера клиенту («Добавил в чат вашего нового менеджера @cathieremozo»)
- Пустое сообщение, «Проверьте», одно слово без бизнес-контекста

## 6. Категория «Другое» — строго

«Другое» — это КРАЙНИЙ случай. Прежде чем поставить «Другое», проверь, не подходит
ли ЛЮБАЯ из тематических категорий ниже. Если подходит хотя бы одна — ставь её.

**НЕ «Другое», а тематическая категория, если в обращении есть:**

- Запрос/подписание/обновление документов: закрывающие, ЭДО, акты, счёт-фактура,
  инвойс, РСВ, 6-НДФЛ, отчёт за период, договор/оферта, справка/письмо для
  визы / ВНЖ / банка / трудоустройства, реквизиты организации → **«Запрос документов»**.
- Верификация третьего лица / «продублировать / перенести / объединить верификацию
  или профиль исполнителя из одного кабинета в другой», «объедините исполнителей
  <ФИО/email>» → **«KYC»** (подкатегория «Дубликат/объединение профиля»).
- Курс вывода / курс ЦБ / разница курса / комиссия / лимиты по картам / «как убрать
  лимит» / ограничения по выводу (в т.ч. крипта/USDT) → **«Курсы/комиссии/лимиты»**
  (executor) или **«Функциональность сервиса и возможность выплат»** (customer).
- Отмена/удаление приглашений исполнителям, изменение данных исполнителя/заказчика,
  объединение аккаунтов → **«Изменения в профиле…»** / **«Изменение/удаление аккаунта»**.
- Ошибка импорта задач, пропали данные услуги, статус задачи, «не открывается ЛК»,
  «абракадабра/язык интерфейса» → **«Техническая проблема/вопрос»**.
- Общий вопрос «как / можно ли / что делать», влияние нового закона / санкций на
  услугу, применимость сервиса для стран/валют, создание категории услуги →
  **«Вопросы по работе в сервисе»**.

**«Другое» ставить ТОЛЬКО когда НИ ОДНА тема не подходит:**

- Технический мусор: «/start», «тест», «ok», одно слово, число, эмодзи
- Обмен формальностями без вопроса: «спасибо», «до свидания», приветствие
- Оргчат сотрудников заказчика: «я в отпуске / передал коллегам», «буду вне доступа»,
  графики отпусков сотрудников, поздравления с днём рождения
- Нечитаемый / битый текст; спам; попытка написать в чужой сервис

Короткое содержательное сообщение ≠ мусор. Если есть хотя бы один тематический маркер — это **тематическая категория**, не «Другое».

## 7. Короткое сообщение + маркер = тематическая категория

Длина сообщения **не влияет** на выбор категории. Запрещено ставить «Другое» для коротких сообщений, если в них есть смысловой маркер.

| Пример сообщения | Категория |
|---|---|
| «Не могу вспомнить пароль» | Техническая проблема/вопрос |
| «ЛК не открывается» | Техническая проблема/вопрос |
| «личный кабинет не откроется» | Техническая проблема/вопрос |
| «не удалось активировать учётную запись» | Техническая проблема/вопрос |
| «Не приходит код» | Техническая проблема/вопрос |
| «Аккаунт уже существует» | Техническая проблема/вопрос |
| «Статус ожидает висит третий день» | Выплаты и проблемы с ними |
| «Не пришла выплата» | Выплаты и проблемы с ними |
| «почему на балансе 0» | Выплаты и проблемы с ними |
| «Выводы не работают» | Выплаты и проблемы с ними |
| «Подтверждение закрытия ИП» | Налоговый статус исполнителя / Статус ИП РФ/Самозанятого |
| «Как поставить статус ИП» | Налоговый статус исполнителя / Статус ИП РФ/Самозанятого |

## 8. Критичное правило: `rationale` ↔ `category`

Если в поле `rationale` написано «это относится к категории X» / «проблема с Y» / «связано с темой Z» — в `category` **обязана** стоять именно эта тематическая категория, не «Другое».

Если `rationale` упоминает: налоговый статус, верификацию, выплату, пароль, документы, регистрацию, удаление аккаунта, курсы, комиссии — ставить соответствующую тематическую категорию.

**Не убегать в «Другое» при сомнениях — выбирать наиболее вероятную тематическую категорию.**

## 10. Подкатегории (subcategory)

Подкатегории определены для двух категорий: «Выплаты и проблемы с ними» и «KYC».
Для всех остальных категорий `subcategory = ""`.

### 10a. «Выплаты» и разведение с «Зачислением на баланс»

**Важно:** «Выплаты и проблемы с ними» = ТОЛЬКО **исходящие** платежи исполнителю
(вывод с платформы / выплата фрилансеру). **Входящее** пополнение баланса
(заказчик отправил деньги на платформу, просит зачислить) — это **отдельная
категория «Зачисление платежа на баланс»** (для обеих сторон), НЕ «Выплаты».

Маркеры «Зачисление платежа на баланс»: «отправили платёж, зачислите на баланс»,
«проверьте пополнение», «деньги ушли в ваш банк — когда появятся в ЛК», скрин/хеш
входящего перевода (USDT-tx, инвойс на пополнение).

### Подкатегория (subcategory) для category = «Выплаты и проблемы с ними»

Заполняется ОБЯЗАТЕЛЬНО, ровно одна из пяти:

| Подкатегория | Когда выбирать | Маркеры |
|---|---|---|
| **Зависание в обработке** | выплата запрошена/отправлена и «висит», долго идёт, нет финального статуса; сюда же общие «где деньги / когда придёт» без иной конкретики | «висит в обработке», «в процессе больше часа», «stuck in process», «сколько ждать», «где мои деньги» |
| **Уточнение причин отказа по платежу** | платёж **отклонён / отказан**, ЛИБО деньги **не дошли / вернулись**, ЛИБО запрос **отменить / вернуть** платёж — суть: разобраться почему не прошёл / вернуть-отменить | «отклонён проверкой безопасности», «отклонены правилами СБ», «card declined», «банк не принял», «деньги вернулись», «не дошли», «отмените выплату», «верните деньги» |
| **Изменение реквизитов** | сменить/добавить карту, кошелёк, счёт получателя; вывод на другие/чужие реквизиты; уточнения про другие реквизиты | «сменить карту», «добавить новую карту», «вывод на другую/чужую карту», «другой кошелёк», «поменять реквизиты выплаты» |
| **Комиссия/курс/лимиты** | вопрос про размер комиссии / курс конвертации / лимит — **в контексте конкретной выплаты** | «есть комиссия?», «по какому курсу выплата», «превышен лимит на вывод» |
| **Документы по выплате** | нужен платёжный документ: акт / инвойс / платёжка / платёжное поручение / выписка о выплатах / transaction receipt / хеш операции. **Сюда попадают ВСЕ запросы платёжных документов** (даже без отдельной проблемы с выплатой) — а не в «Запрос документов» | «нужен акт по выплате», «пришлите платёжку / платёжное поручение», «invoice — банк просит», «transaction receipt with date/time», «выписка что выплаты ушли в даты», «хеш операции» |

> Если кейс одновременно про «висит» и «почему отклонён» — приоритет у того, что
> является сутью обращения: есть факт отказа → «Уточнение причин отказа»; просто
> долго без отказа → «Зависание в обработке».

### 10b. Подкатегория (subcategory) для category = «KYC»

Заполняется ОБЯЗАТЕЛЬНО, ровно одна из шести:

| Подкатегория | Когда выбирать | Маркеры |
|---|---|---|
| **Запрос на верификацию** | **дефолтная подкатегория** для любой просьбы провести верификацию: заказчик передаёт исполнителя(ей) на KYC, исполнитель просит верифицировать себя, общие «не получается / не могу пройти верификацию» БЕЗ явного технического сбоя загрузки и без озвученной ботом причины отказа; сюда же вопросы «как пройти / какие документы нужны» | «ФИО + email на верификацию», «помогите верифицировать исполнителя», «верифицируйте меня», «не получается верифицировать», «не могу пройти KYC», «как пройти KYC», «какие документы нужны для верификации» |
| **Уточнение причины отказа** | верификация **отклонена**, клиент уточняет почему; бот/система озвучили причину (регион/документы/предел загрузок) | «почему верификация отклонена», «не удалось верифицировать — регион не поддерживается», «достигнут предел загрузки документов», «документы отправлены в другой профиль», «отмените отклонение» |

| **Повторная/сброс верификации** | просьба сбросить пройденную/проваленную верификацию и пройти заново | «сбросьте верификацию», «дайте пройти заново», «обнулите KYC», «перезапустите проверку» |
| **Ошибка прохождения** | **узко** — только явный технический сбой интерфейса/загрузки: файл не загружается, страница/кнопка не работает, падает с ошибкой системы. НЕ использовать для общих «не получается верифицировать» (→ Запрос на верификацию) и НЕ для озвученного отказа (→ Уточнение причины отказа) | «не загружается селфи/фото паспорта», «кнопка отправки не работает», «страница верификации виснет/падает», «ошибка 500 при загрузке», «verification_failed (системная ошибка)» |
| **Дубликат/объединение профиля** | перенос/дублирование пройденного KYC между кабинетами, объединение дублирующихся профилей (бывшая категория «Дублирование KYC») | «продублировать верификацию из кабинета A в B», «перенести KYC в другой кабинет», «объедините профили» |

> **Приоритет при пересечении:**
> - есть озвученная причина отказа → «Уточнение причины отказа»;
> - явный технический сбой загрузки/UI → «Ошибка прохождения»;
> - долго висит без отказа → «Зависание верификации»;
> - во всех остальных случаях (общая просьба/«не получается»/вопрос как пройти) → «Запрос на верификацию».

## 11. Outbound от поддержки

Сообщения от `@madetask`, `@remozo`, `RemozoSupport`, `@MadeTask_*`, а также типовые исходящие фразы:
- «Thanks for reaching us»
- «We have changed your profile status»
- «Благодарим за ожидание»
- «Направляем запрос специалистам»
- «Ваш профиль был успешно верифицирован»

— это **outbound от поддержки**, не клиентское обращение.

Для определения `side` и `category` ориентироваться на следующий по смыслу **inbound** от клиента.
Если содержательного inbound вообще нет → `category = "Другое"`, `rationale = "нет содержательного обращения клиента — только outbound от поддержки"`.

## 12. Поля ответа (JSON)

| Поле | Тип | Допустимые значения |

**Примеры корректного `rationale`:**

Цитата должна быть **реальной фразой** из inbound-сообщения.
